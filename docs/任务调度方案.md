# 并发与任务调度方案

## 1. 产品策略

这里的“并发”是**多个任务可提交、任务在后台排队执行、画布编辑不被等待阻塞**，不是多张图同时占用 GPU。对单台设备的图像生成，先采用单任务串行执行，避免显存竞争和多个结果同时挤占用户注意力；用户等待期间仍可调整版式、文字和图层。

目标产品中的推理必须留在设备本地。任务失败、模型未就绪或设备资源不足时应明确提示，不允许把请求切到云端完成。

## 2. 一项任务的状态和结果

1. **提交：** 校验输入和模型状态，创建独立任务记录。
2. **排队：** 显示队列位置；排队中的任务可以取消。
3. **执行：** 单 worker 运行本地模型并报告阶段/进度；画布继续响应编辑。
4. **完成：** 输出作为独立候选素材显示。用户预览并选择「置入画布」才增加图层；不会覆盖现有画布。
5. **失败：** 显示可理解的失败原因；用户主动重试时创建新任务，保留旧失败记录。
6. **保存：** 项目图层、快照和本机草稿与任务结果分开管理。正常刷新/重进可恢复画布，不因结果完成而改写草稿。

## 3. 取消、中断和恢复边界

### 目标本地任务

- 排队任务取消后不启动。
- 运行任务接受取消请求；如果模型只能在安全的进度检查点响应，用户可能需要等待当前计算段结束。不能承诺点击后立即终止。
- 取消后丢弃未确认的任务结果，不将其自动放入画布。
- 进程重启时，已排队任务可按持久记录重新进入队列；重启前运行中的任务标记为中断，由用户决定是否重试。
- 不承诺扩散过程断点续跑。画布草稿恢复与模型任务恢复是两件事：草稿从快照恢复，生成任务只能重新提交。

### 当前原型实际做法

- 任务记录与项目数据落在本地存储；队列由单个后台 worker 串行处理。
- 本地 U2Net 任务取消标记为 `cancelled`；现有执行器在后续进度回调处停止并丢弃结果，取消不一定瞬时停止。
- 当前文生图请求发往百炼。取消运行中的云端请求只能停止本地等待，不能保证远端停止；状态标记为 `interrupted`，提示用户先核对远端，且不自动重提。
- 重试需要用户操作；对中断的云端任务必须先确认远端状态，且再次生成前需要费用确认。

云端状态处理仅为当前原型防止意外重复请求的防护。目标产品方案不设置云端推理服务。

## 4. 连续提交三项任务的例子

以“同一商品制作三种背景候选”为例（目标本地方案）：

| 时间 | 任务队列 | 用户可继续进行的操作 |
|---|---|---|
| T1 提交 | 任务 A 运行，B/C 尚未提交 | 画布继续编辑标题与商品摆放 |
| T2 提交 | A 运行，B 排队第 1 位 | 调整角标颜色；画布显示保存状态 |
| T3 提交 | A 运行，B 第 1 位，C 第 2 位 | 切换图层或微调文案，不等待生成完成 |
| A 完成 | A 候选进入结果区；B 开始 | 用户可预览 A；不点击确认则画布不变化 |
| B/C 完成 | 各自候选进入结果区 | 用户分别选择需要的结果并置入画布 |
| 任一失败 | 该任务显示原因，其余继续 | 用户可稍后重试失败项；重试创建新任务 |

若 A 已不需要，可取消排队中的 B；若正在运行的 A 被取消，按本地模型可响应的检查点停止。任务完成与用户选用是两个独立动作。

**当前原型验证边界：** 队列/取消/状态流转已有自动化覆盖；没有连续提交三项真实背景生成，因为生成走可能收费的云端服务，且本地生成模型未实现。因此上述“三项任务”是目标交互策略，不是本地生成实测。

## 5. 方案取舍

- **选择串行推理：** 单机显存有限，先保证任务稳定与成品质量；并发体验通过队列可见和画布可编辑实现。
- **不自动放入画布：** 保留用户决定权，防止迟到的任务覆盖正在编辑的内容。
- **不自动重提中断任务：** 避免结果重复和不确定的费用；由用户核对后明确重试。
- **不承诺断点续跑：** 扩散采样中断后无法由当前原型可靠续接；需要诚实展示“重新运行”，而不是宣称继续上次进度。
- **不扩展成商业级调度：** 当前方案只覆盖单机任务队列、取消/失败处理和草稿保护，不建设分布式 worker、云端算力池或计费系统。
